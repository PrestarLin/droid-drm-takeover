## 0. 目标、硬件与环境

### 0.1 目标
在小米 Pad 8 Pro 上**停掉 Android 显示栈，由容器里的 Linux（kwin_wayland/Plasma 6.6.6）直接驱动 3200x2136@120 双 DSI 面板**（KMS takeover），不再经过 Anland 画面转发。当前已达：真实合成器画面（es2gears）稳定上屏 + 真手指触摸可用（尚有卡顿，见第 5 节）。

### 0.2 硬件/系统
- 设备：Xiaomi Pad 8 Pro，SoC SM8750（piano），Adreno 830，面板 3200x2136 双 DSI pipe，120Hz（官方帧参考 fps:144）。
- 内核：6.6.118-android15（vendor msm_drm 1.4.0 + sde），HyperOS，SELinux Enforcing。
- Linux 侧：安卓里跑的 **Droidspaces 容器**（Ubuntu resolute + KDE），会话由 `/usr/local/bin/startanland-kde.sh` 拉起（kwin_wayland_wrapper → kwin `--wayland-fd 7 --socket wayland-0 --xwayland`，`ANLAND=1 ANLAND_SOCKET=... ANLAND_DRM_DEVICE=/dev/dri/renderD128 MESA_LOADER_DRIVER_OVERRIDE=kgsl`）。
- 容器 PID1=systemd，systemd-logind 活跃且有 seat0；容器 GL 栈 = **stock Ubuntu Mesa（freedreno msm_dri.so + dri_gbm，走 kgsl 节点）**，kgsl_dri.so 来自 `lfdevs/mesa-for-android-container` fork（Mesa 26.1.0-devel）。
- 控制通道：容器 → adb over WiFi（`10.166.147.104:<端口>`，**端口每次重连会变**；本轮会话经历 36031→43439→44295→38851→36263→36933→33575）；安卓侧 root 走 `adb shell "su -c '...'"`（KernelSU）。注意 `su -c "a; b"` 的双引号会被本地吃掉且只有首条是 root，**必须整体套一层单引号**。

### 0.3 为什么现在能看见节点（容器 DRM 通路）
- Droidspaces 默认在 `src/mount.c: prune_host_devices()` + `src/hardware.c: is_dangerous_node()` 里删除 card*/controlD*/fb*/tty（理由注释：card 需要 exclusive control/DRM master）；逃生门 `--privileged=unfiltered-dev`（config.c:84）。
- 实际**不需要改 Droidspaces**：容器 /dev 是无 nodev 的 tmpfs，root 直接 `mknod /dev/dri/card0 c 226 0` 即可（**/tmp 带 nodev，节点建那儿会 EACCES**）。HyperOS 这个 build card0 权限 666。
- 容器重启后节点丢失需重建：`mknod /dev/dri/card0 c 226 0`、`mknod /dev/input/event11 c 13 75`，均 `chmod 666`（脚本已自动做，drm-takeover.sh 第 67-71 行）。

## 1. 最终架构总览（kwinwrap + split_commit + udev 合成）

```
安卓侧(adb root)                      容器(root→uid1000)
stop SF + composer  ──────────────►   kwinwrap: open card0 → SET_MASTER → 预清理(关安卓plane)
                                      → ioctl DRM_DROP_MASTER_REQ(0xC004641F) → exec kwin_wayland
                                      kwin 自己 openat card0 → 按"首开自动 master"成为真 master
                                      ptrace 挂 ioctl #29(ATOMIC) entry/exit：
                                        · 第一次 ATOMIC 原样执行探模式：ret != -EACCES 判 NATIVE
                                          （TEST_ONLY 合法失败 -22/-2 也算 native，只有 -13=非master）
                                        · split_commit：提交里的 plane 97/129 条目原地换成
                                          161(左半)+157(右半)，同 FB、SRC_* 16.16 半宽、
                                          CRTC_* 整数半宽，各扫 1600x2136；
                                          新数组写在线程 SP 下方 scratch (r->sp-0x8000)
                                        · EVDROP：从带 flip 事件的提交里剔除未激活 crtc 的对象
                                      udev 合成 /run/udev/data/c13:75 → libinput 认 event11 为
                                      DIRECT 触摸屏 + LIBINPUT_CALIBRATION_MATRIX 转 90°
PERSIST 保活: ctl.stop system_suspend + wake_lock + keepbright.sh(5s 钉背光)
```

要点与理由：
1. **DROP_MASTER 交接**（不是 relay）：此前 relay 方案的 flip 事件饿死根因 = 事件挂在 kwinwrap 的 drm_file 上，kwin poll 自己的 fd 永远收不到。交接后 kwin 提交/vblank/flip 事件全原生。
2. **split_commit 双 pipe 是花屏真因与解法**：kwin 从 GETRES 改写后的资源里选 primary plane，**选 97 还是 129 每轮随机**（都是单 pipe legacy 虚拟平面，直接上屏必花屏，暗/亮噪点只是表象）。解法即上面的条目替换；两个虚拟 plane 同现时：第一个拆分、第二个直接剔除。改写后由 kwin 自己执行 ioctl → ret/事件天然正确。
3. **FD_MESA_DEBUG=noubwc**：强制 GBM bo 线性，与 AddFB2 无 modifier（内核记 mod=0x0）一致。上一轮花屏时 mod=0x0 但 bo 可能实际 UBWC。
4. **容器 GL 不需要 kgsl 特殊路径**：kwin 用 stock Mesa 的 GBM+EGL（renderD128）已正常；瓶颈在 KMS 提交侧不在 GL。

## 2. 内核与厂商行为备忘（本 vendor kernel）

- **DRM_CLIENT_CAP_ATOMIC 必须开**（fd 级），不开时任何带属性的 MODE_ATOMIC 返回裸 EINVAL、内核零打印。同时开 UNIVERSAL_PLANES(=2)；**ATOMIC 枚举值=3（不是 5！）**；SET_CLIENT_CAP ioctl=`0xC010640D`。
- **connector 67 没有 MODE_ID 属性**（枚举 32 属性确认；全局只有 23 一个 MODE_ID，属 CRTC 侧）。往 conn 设 23 → ENOENT 打死全请求。正确做法：模式只设 `crtc ACTIVE=1 + crtc MODE_ID=blob`，conn 只设 `CRTC_ID=206`。
- **plane 坐标系**：SRC_* 是 16.16 定点，CRTC_* 是整数像素。给 CRTC_X/Y/W/H 左移 16 位 → sde 报 `plane161 invalid dest rect`(-22)。
- 属性查找按全局 pointer 匹配，"attach 与否"不拦 UAPI（attach 列表是表象，别被误导）。
- **TEST_ONLY 也要求 DRM master**（否则 EACCES）→ 一切探测都得在停 SF+composer 的脚本里跑。
- 内核 atomic 属性按**全局 ID**寻址（见第 9 节速查表）；对象 ID **每次重启会变**，用前先 dump（debugfs state / GETRES）。
- msm_drm 调试开关（安卓侧 su 写；容器 /sys 只读）：
  - 开：`drm/parameters/debug=0xffffffff`、`msm_drm/parameters/debugpolicy=0x3f`、`debug_level=0xffffffff` → sde_plane_atomic_check 拒绝原因全打出。
  - 收（drm-stop.sh 已做）：`0x0` / `0x20` / `0x0`。
- debugfs 在安卓侧被**混淆到 `/dev/cqounyos/zkbhwkxl/dri/0/`**（state/framebuffer/clients 都在这里，不是 /sys/kernel/debug；脚本另一分支也试过 `mount -t debugfs none /sys/kernel/debug` 后走标准路径——两处都探一下，以实际存在为准）。debugfs clients 表可直接看 master 列。
- **evdev 内核去重**：注入值与设备当前存储值相同的事件被内核直接丢弃（sendevent 验证时 X/Y/TRACKING_ID 每次必须换新值，否则误判链路不通）。
- **system_suspend 服务**是整机 suspend 唯一发起者；composer 死了以后 PowerManagerService 会 3~6 秒一轮空转熄屏（见 3.1 panic 根因）。
- hangdetect 驱动：`drivers/xiaomi/hangdetect/hang_detect.c:1451` 有 BUG()，D 态超时计数 5:5→-1:5 即 kernel panic。
- 官方 composer 帧参考值（dmesg 抓到）：XR24/UBWC mod `0x500000000000001`、sspp 高按 16 对齐(2144)、topology:5、fps:144；我们的线性 XR24 mod=0 也被 check 接受；core_ab=6.8GB/s 参考。
- HyperOS 坑集合：
  - `ctl.start surfaceflinger` 会重新拉起 bootanimation 且**永不自停**（boot_completed=1 触发器不再发）→ 必须补 `setprop ctl.stop bootanim`（drm-stop.sh 里做了两次）。
  - composer 服务名**没有 -service 后缀**：`setprop ctl.restart vendor.qti.hardware.display.composer`（带后缀 Failed to set property）。
  - 唤醒/熄屏**只用 keyevent 224**；26/82 会触发 HyperOS 相机手势。
  - `/usr/bin/kwin_wayland` 直接跑会被 <0.5s SIGKILL——杀手按 **exe 路径**匹配（改名副本存活、strace 附加存活 20s）；接管时安卓 UI 整体下线杀手随之消失；兜底=用副本路径起。

## 3. 已解决问题全记录

### 3.1 【09-22 核心】常驻接管后 kernel panic / 屏幕明暗跳变 / 反复断网 —— 已根治
- 症状：接管成功后屏幕周期性明暗跳变、WiFi 反复断流（多次逼用户硬重启平板）、最终一次真 kernel panic。
- pstore 取证（/tmp/ramoops1.bin 2MB console）确认链条：
  1. 接管停了 composer/sf → Android PowerManager 走熄屏 → `android.system.suspend-service` **每 3~6 秒发起整机 suspend**；
  2. 每轮都在 `cnss_pci_suspend` 失败（WLAN PCIe 恒返 -11 EAGAIN）→ `PM: Some devices failed to suspend` → 无限重试 → **屏幕明暗跳变 + 断网**；
  3. 最终一次 QTEE SMC 调用卡死（`adci_thread` D 态 150s+，si_core_module/U_scm_smc_call）→ hangdetect 计数 5:5→-1:5 → **kernel BUG at hang_detect.c:1451**。
- 修复（已进 drm-takeover.sh PERSIST 分支）：接管成功即
  `setprop ctl.stop system_suspend` + `echo qoderdbg > /sys/power/wake_lock` + `settings put system screen_off_timeout 2147483647` + 背光 2048 + 后台 keepbright.sh。
- 验证：boot@15:51（adb 43439）15:57 接管成功起，dmesg **零 suspend/熄屏事件**，内核存活 35+ 分钟（此后的重启都是断网逼的人为重启，bootreason=reboot，非 panic）。旧 36031 那轮断网同因。
- **注意**：断网问题并未被此修复完全消灭——有一次断网**没有** getevent 也没有 suspend 日志可归因（见第 5 节），但 getevent 相关性仍最强（见 4.4）。

### 3.2 【09-21】花屏（暗/亮噪点满屏）—— 根因：kwin 选中单 pipe 虚拟 plane
见 1.2：plane 97/129 是 legacy 单管虚拟平面，vendor 双 pipe 面板必须走 161+157 成对。split_commit 在 ptrace entry-stop 时原地改写提交数组。验证快照：debugfs state 里 plane157+161 同 fb、crtc-0(206) enabled、97/129 全 null。

### 3.3 【09-21】flip 事件饿死（relay 方案）
事件挂在 kwinwrap 的 drm_file，kwin poll 自己的 fd 永远收不到 → 改 DROP_MASTER 交接，kwin 自己当 master。

### 3.4 【09-21】三个 atomic 打地鼠（全部有实证）
1. 没开 ATOMIC cap → 裸 EINVAL 零打印（rawprobe 第 1 轮开 cap 后 ACTIVE/CRTC_ID/SRC_X/FB_ID 单属性 TEST_ONLY 全 ret=0）；
2. conn 无 MODE_ID → ENOENT 打死全请求（rawprobe 第 2 轮 L 用例）；
3. CRTC_* 误做 16.16 移位 → dmesg `plane161 invalid dest rect`(-22)。
S1-S3 阶段（点亮 CRTC+模式+路由）TEST_ONLY 全绿后进入合成器阶段。

### 3.5 【09-21】DRM master 到底在谁手里
- 只停 SF：SET_MASTER 24 次轮询全 EBUSY；同时停 SF+composer：**第 1 次（约 2.5s）即成功**。
- debugfs clients 表实锤：**master 持有者 = `vendor.qti.hardware.display.composer-service`，不是 surfaceflinger**。
- ksu SELinux 域（Enforcing）允许 open card0 + SET_MASTER；恢复 ctl.start composer→SF 后 master 回新 composer，全链路无损。

### 3.6 【09-21】接管后"恢复安卓全黑"三段处置（实战）
症状：色带 60s 结束、trap restore 跑完，屏幕仍全黑、keyevent 无效。分层排查工具：screencap（纯黑 PNG≈32KB）、crtcstate（mode_valid/DPMS/**brightness**）、planeprobe（plane 全 crtc=0=composer 没提交）、`dumpsys power | grep mWakefulness`（Awake/Asleep 横跳）。三个叠加真因：
1. **背光卡死在 dim 最低档 0.0017（≈2nit）**，composer 重启不恢复 → `bin/setbright 2048`（conn67 prop87 "brightness"，0..4095，SETPROPERTY **不需要 master**）；
2. **系统反复回睡** → `keyevent 224` 后立刻 `wm dismiss-keyguard` + `am start -a android.settings.DISPLAY_SETTINGS` 钉 Awake + screen_off_timeout 拉满；
3. **composer HAL 状态坏死** → `setprop ctl.restart vendor.qti.hardware.display.composer`（无 -service 后缀），再 restart surfaceflinger。
面板残留静止开机动画帧 = 显示已恢复但没重绘 → `input tap 800 400` + `input swipe 1400 1900 1400 1000 250`。

### 3.7 【09-21】触摸画图 touchdraw 打通（第一轮输入）
- 必须 event11（13:75，NVT-ts 内核直出）；event9 "Xiaomi Touch" 是 Bus=0006 (15d9:00a1) 的 uhid 镜像，靠安卓服务喂数据，停 SF 后彻底静默。

- 二进制 stdout 重定向进日志是**全缓冲，段错误吞输出** → touchdraw 加 `setvbuf(stdout,NULL,_IOLBF,0)`。

### 3.9 脚本工程教训
- adb→su -c→设备 shell 三层引号会打碎管道 → 改成 `run "dmesg"` 拉回容器本地 grep。
- `bash -c` 里同时含 pkill 模式文本和被杀命令 → pkill 自杀（exit 143）→ 用 `ps -ef | grep xx | grep -v grep` 确认 + 用编辑工具改文件。
- shell 重定向 `nohup X >> log 2>&1 > /dev/null` 把 stdout 又指回 /dev/null → 采集 90s 全空（两次）。
- `/dev/kmsg` 是流设备，`grep -c . /dev/kmsg` 会挂死 shell。
- drm-takeover.sh 的 EP 端口列表不含新端口 → 脚本卡着一轮连接旧端点白费 → 每次换端口先更新第 24 行 EP 列表。
- 首版 PERSIST 编辑里曾写 `echo freeze > /sys/power/autosleep`——那是**启用** autosleep，已删。

### 3.10 【09-22】齿轮帧率极低、整机卡（U157 报告）→ 已解决
- 现象：kwin 画面首次上屏（relay/kwinwrap 转发提交时代）后"帧数很低，设备很卡"。
- 定量瓶颈：relay 模式下每次提交要跨进程转发 + kwin 仍在跑 TEST_ONLY 预检（实测 **TEST ~51ms + flip ~28ms**/次），且 flip 事件饿死迫使 kwin 走保守节流。
- 解决组合：①DROP_MASTER 交接让 kwin 成原生 master（事件/提交不再转发）；②ptrace 探测判 NATIVE 后**跳过改写提交里的多余流程**；③EVDROP 修复（从带 flip 事件的提交剔除未激活 crtc 对象）让事件流正常；④工作翻转 `0x201` 稳定后 **exec 降至 0.2~1ms**（kwinatomic.log 实测 `f=0x201 ret=0 exec=298us`）。
- 现状：用户确认"齿轮非常流畅"（U196）、后续多轮无掉帧报告 → task #10 事实达标，仅剩长稳观察。

## 4. 触摸链路（2026-09-22 打通）

### 4.1 设备与坐标
- **唯一可用节点：event11 "NVTCapacitiveTouchScreen"（13:75，NVT-ts 内核直出，virtual input11）**；INPUT_PROP_DIRECT；MT 10 slots、协议 A（SLOT 前置+TRACKING_ID，-1=抬起）；另报 TOUCH_MAJOR/PRESSURE(0/1)。接管期间 NVT 驱动保持 awake（bTouchIsAwake:1）无 suspend。
- 原始坐标**竖屏系+转置**：ABS_X 0..213599（短边）、ABS_Y 0..319999（长边），单位 0.01mm。横屏面板映射：`cy = H-1-x/100` 纵向翻转、横向直接用（这是 touchdraw 手写 evdev 时的公式）。
- event9 "Xiaomi Touch"（13:73，像素系 0..3199/0..2135）：**接管期间无真手指数据**——曾按旧笔记猜它是手指节点，决定性抓取（接管中 /tmp/during.log 480 行真手指事件全在 event11）证伪。

### 4.2 kwin/libinput 侧接线
1. **udev 合成**（脚本第 82 行，写 `/run/udev/data/c13:75`）：`ID_INPUT_TOUCHSCREEN=1` + `H:seat=...` + `H:uaccess` + `LIBINPUT_DEVICE_GROUP=11/6/15d9:NVTCapacitiveTouchScreen` + **`E:LIBINPUT_CALIBRATION_MATRIX=0 1 0 -1 0 1 0 0 1`**。
2. 校准矩阵语义：x'=y_norm、y'=1-x_norm（90° 旋转），libinput 1.31.1 从 udev 文件读取，kwin 应用；实测 QPointF(2399.99,1536) 与手算一致，touchtest 收到正确坐标。
3. 验证后 kwin 实际持有 /dev/input/event11（fd 27）+ input capture keymap，libinput 识别为 cap:t DIRECT。

### 4.3 验证方法（在 getevent 禁令下）
- `bin/touchtest`（已加打点：`printf("touch down id=%d at %d,%d (surface %dx%d)\n",...)`，全屏红边+橙点，`setvbuf` 行缓冲）→ 看 /tmp/ttA.log。真手指 27 条 down、坐标线性 → 用户口述"测试触摸可用"。
- kwin.log 的 "touch down" 行也可作旁证。
- 合成注入（sendevent → event11）做端到端验证时，**每个 tap 用新的 X/Y/TRACKING_ID**（2.10 的去重坑）。
- 编译：`cc -O1 src/touchtest.c src/xdg-shell-protocol.c -o bin/touchtest -lwayland-client`（不链系统 xdg-shell 生成码，用仓内副本）。

## 10. ANLAND/Mesa 侧分析结论

- 开关 `MESA_LOADER_DRIVER_OVERRIDE`：未设=zink→turnip→kgsl；`=kgsl` 时 EGL wayland/surfaceless/drm 拿不到 wl_drm/DRM fd 就直接 `loader_open_device("/dev/kgsl-3d0")`；gallium `kgsl_driver_descriptor`（DRM_DRIVER_DESCRIPTOR_ALIAS(msm,kgsl)）；Vulkan `tu_knl_kgsl.cc`（gen7/8 现代 ABI，Adreno 830 可用）。
- **缓冲模型只进不出**：kgsl 能 `GPUOBJ_IMPORT` 导入 dmabuf，但 kgsl 自分配 bo **导不出 dmabuf**（gen7 kgsl uapi 无导出 ioctl，`kgsl_bo_dmabuf()` 只是 dup(import_fd)）。所以 anland 方向=Android gralloc 分配→递进容器→Mesa 导入渲染→交回安卓上屏；GPU 是消费者。
- **它不能直接 KMS 直显的三个断点**：kgsl bo 无导出（要改内核 kgsl）、gbm backend 无 kgsl fd 适配、kgsl 堆与 mdss 显示 SMMU 无映射约定。KMS 方向相反（GPU 分配→导出→AddFB2→flip）。
- **对本项目结论：接管不需要动这套 Mesa**。kwin 用 stock GBM+EGL 已工作（瓶颈在 KMS 提交侧：曾测 TEST 51ms + flip 28ms 量级，与 GL 驱动无关）。可借鉴思想=显示端分配+GPU 导入（app dmabuf 不经合成直上 overlay，要动的是 kwin/协议）。
- 该系 Mesa modifier 怪癖备案：LINEAR(0) 被改写 1274(0x4FA)；implicit modifier 需直走 dmabuf 提交；linux-dmabuf 只有 v3。
- 现状架构参考（为什么以前必须转发）：Anland v5 = 安卓 consumer 从 BufferQueue dequeue gralloc dmabuf，SCM_RIGHTS 过 socket 给容器 daemon，补丁 KWin(anland backend) 在 surfaceless EGL 上画进去带回 SF 上屏；Droidspaces 刻意为防接管剪掉 card 节点。备选路线对比：A 本方案(最快) / B 主线内核 simpledrm(正统但 panel/DSI 硬骨头) / C UEFI+simplefb(风险高一档) / D 继续 Anland 转发(现状)。
